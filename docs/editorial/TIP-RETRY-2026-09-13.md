# Liv tip reload recovery

Local implementation, not deployed yet.

- Existing API idempotency remains unchanged. Before submission the client saves the exact operation ID, URL and angle in UID-scoped versioned sessionStorage.
- Reload or navigation in the same browser tab restores the pending request, locks its fields and requires an explicit retry. No automatic submission or paid research.
- Confirmed success clears only the matching receipt; missing response, 503, authentication failure and 409 preserve it. Definitive validation 400/413 allows correction after removing the matching receipt.
- Corrupt/unavailable storage is not silently discarded or converted into a new request. Storage reading has an explicit retry. SessionStorage does not promise recovery after closing the tab or across devices.
- The tips component is keyed by UID. Unmounted mutation responses cannot clear another user's receipt or update their screen.

Verification: 17 targeted storage/API/selection tests passed. The real LivTips component was tested with isolated fake auth/API via `scripts/verify-tip-retry-ui.mjs`: simulated first 503, reload, B sees empty fields/no extra POST, switch back A, retry sends identical body/token, successful receipt clears storage and fields. No browser errors. Mobile 390×844 screenshot `/tmp/tip-retry-mobile.png` inspected. Browser/server closed.
